## 1. 背景与现状问题

现行拼车规则（migration 182）：

- 按人头定容量：小车每级 5 席（基础费 ¥130/席）、大车每级 10 席（¥65/席）；
- 开车后所有成员拿到同一分组下的订阅，**限额全 NULL、不限量**；
- 用量池费用按成员相对用量比例事后分摊（纯文案，无系统实现）。

核心问题：

1. **人数限制与真实用量脱钩**。固定 5 人或 10 人是拍脑袋容量，"要么周限用不完、要么周限超上限"是结构性必然。
2. **公地悲剧**。全员共享无上限池子，先用先得，没人有节制用量的激励。
3. **费用无承诺机制**。上车不预付，事后分摊缺乏约束力；虚报用量零成本。

## 2. 设计目标

用**额度预约制**替代**人头席位制**，达到激励相容：

- 上车前**申报一周预期额度**（USD 计价），**按申报量预付第一笔账**；
- 申报额的 **80% 定向锁定**给本人，**20% 进入机动公共池**先到先得；
- 总申报达到整车周限额的 **95%–105%** 即可发车；
- 席位费保留（固定成本覆盖 + 鼓励多用）；
- 周期结束**按实际用量对变动部分多退少补**，且**计费用量不低于申报的 80%**——报多少保底多少，保底多少至少付多少。

## 3. 核心参数

| 参数 | 含义 | 取值 |
|---|---|---|
| `weekly_limit_usd` | 整车（Pro 20x 账号）周限额，USD 计价 | **$2400 / 周** |
| `plus_equiv_usd` | 1 个 Plus 账号等价周额度 | **$120 / 周**（2400 = 20 × Plus） |
| `seat_fee_cny` | 席位费（固定部分），全车每月 | **¥400**，按人数均摊（400 / N） |
| `usage_pool_cny` | 变动池（用量部分），全车每月 | **¥1000**，按计费用量占比分摊 |
| `reserve_ratio` | 申报额中定向锁定/保底付费的比例 | **80%** |
| `launch_band` | 可发车的总申报区间 | **[95%, 105%] × 2400 = [$2280, $2520]** |

## 4. 核心机制

### 4.1 申报与容量

- 车的容量 = **周额度池 $2400**，不再有人数上限；
- 用户加入时必填 `declared_weekly_quota_usd`；
- **上车硬上限**：若 `当前Σ申报 + 新申报 > 2520`（105%），**拒绝上车**，提示等待下一辆车；
- 成员数弹性化：申报 $120/周 的轻度用户可拼 20 人，申报 $400/周 的重度用户只拼 6 人。

**申报推荐（降低申报门槛）**：加入对话框自动给出推荐申报值，基于本人使用记录：

- 有 ≥7 天记录：推荐值 = 最近 7 天的实际用量（USD）；
- 不足 7 天（有 n 天记录，1 ≤ n < 7）：推荐值 = `过去 n 天总用量 / n × 7`（按日均外推）；
- 完全无记录（新用户）：给参照锚点文案（如"日均 2 小时编码 ≈ $X/周"，X 按平台历史用户分位数校准），让用户自行估计；
- 推荐值只是预填，用户可改；建议叠加 10–20% 的缓冲系数（如推荐值 × 1.1，可配置），减少低报导致的保底不足。

### 4.2 80% 保底 + 20% 机动公共池（v3.2：公共池硬约束）

开车时按如下方式配置限额（技术实现见 §6.2）：

```
成员保底 r_i        = 0.8 × 申报_i                → user_subscriptions.weekly_reserved_usd
公共池容量 C        = 2400 − Σr_i
个人订阅周限额      = r_i + C                      → user_subscriptions.weekly_limit_usd（个人绝对上限，防呆）
组周限额（安全帽）  = 2400（每订阅语义，见下）
```

**限额执行（两层检查，中间件 + billing cache 语义一致）**：

1. 成员当周用量 `< r_i` → **无条件放行**（保底硬保证，不依赖任何共享状态）；
2. 用量 `≥ r_i`（开始吃公共池）→ 检查**组级公共池计数器** `Σ max(0, usage_j − r_j) < C`，未满才放行；
3. 任何情况下用量 `≥ r_i + C` → 按普通周限拒绝（个人绝对上限防呆）。

**用量记录**：每次计费提交（`usageBillingRepository.Apply`）在同一 `UPDATE ... RETURNING` 内取回新周用量，按增量 `max(0,新−r_i) − max(0,旧−r_i)` 原子累加（INCRBYFLOAT）到组级计数器，key 为 `carpool:commons:{group_id}:{weekly_window_start}`（TTL 8 天）。

**窗口对齐**：发车时全车 `weekly_window_start` 统一为发车日零点（UTC）；拼车订阅的周重置吸附回该 7 天网格（而非"当天零点"），保证全体成员窗口起点恒等、计数器 key 一致，窗口随 `NeedsWeeklyReset` 整体推进、计数器 key 自然轮换。

**保底为什么是硬保证**（新不变式，替代 v3.1 及之前的错误描述）：

- 旧描述称"组限额把整车总量钉死在 2400"——这是**错误前提**：`group.weekly_limit_usd = 2400` 是每订阅语义，平台此前不存在组级聚合用量计数器；每条订阅各自放行 `r_i + C`，合计可达 `0.8Σ + N×C`，远超 2400。
- 新机制下：保底内用量 `≤ r_i` 无条件放行，与计数器无关；超额总量被组级计数器约束 `< C`，故全车 `Σ用量 ≤ Σr_i + C = 2400`（105% 超募时 `C ≥ 16%×2400 = 384 > 0`，机制不失效）。
- 计数器检查是**预检查（TOCTOU）语义**：读旧值后并发 in-flight 请求可同时放行，带来有限超卖（上界 ≈ 并发请求的平均成本），与既有 `CheckWeeklyLimit` 同级，不追求绝对零超卖。

性质：

- 每个人的**保底额度** = 80% 申报值，任何人抢不走（不依赖公共池计数器状态，计数器故障/未注入时保底照常放行）；
- **公共池 C**（20% 机动 + 招募未满 100% 的零头）全员先到先得，鼓励多用；
- 105% 超募上限保证公共池始终 ≥ 16%，保底机制数学上不会失效。

### 4.3 发车

- Σ申报进入 **[2280, 2520]** 区间即满足发车条件，owner（或 admin）手动触发发车（替代现行"满员自动开车"）；
- 可选：给 owner 一个"降档发车"选项（如 Σ ≥ 80% 时强制发车，公共池变大、保底不变），避免招募期卡死。

### 4.4 预付（第一笔账）

上车即记账（线下收款，系统记台账）：

```
每人预付 = 400 / 当前人数 + 1000 × (我的申报 / 2400)
```

- 固定部分按人头均摊——**人越多越便宜，鼓励拉人**；
- 变动部分按申报比例——**申报有真金白银的成本**；
- 满车（Σ = 2400）时全车共收 400 + 1000 = **¥1400/月**。

注意：400/人数 按发车时人数锁定计算；中途加入摊薄席位费的差额，在月末结算单统一找齐。

### 4.5 结算（多退少补 + 80% 地板规则）

订阅有效期 1 个月，月末出结算单。**计费用量**定义：

```
计费用量_i = max(实际用量_i, 0.8 × 申报_i)      ← 80% 地板规则
每人最终分摊 = 1000 × 计费用量_i / Σ计费用量
每人退/补    = 预付变动部分 − 最终分摊
席位费 400 部分不退不补（固定成本）
```

含义：**保底额度是专门为你锁的，用不用都按保底付钱；公共池部分用了才付钱**。
虚报的成本由此内建——报 $400 只用 $100，仍按 $320 计费。

恒等闭合：全车变动池收支恒等于 ¥1000，无窟窿。

### 4.6 展示指标

**车外（拼车广场卡片，未上车可见）**：

- **剩余可预约额度** = `2520 − Σ当前申报`（USD）；
- **Plus 账号等价数** = `Σ申报 / 120`；
- **均价** = `[400 + 1000×(Σ/2400)] / (Σ/120)`（¥/Plus等价/月）。满车时 = 1400/20 = **¥70/Plus等价/月**（对照官方 Plus 约 ¥140/月，半价）；
- 建议同时分档展示不同申报量对应的个人折算单价（见附录 A2 的轻/中/重差异），避免轻度用户上车后对价格结构产生误解。

**车内**：我的保底额度与消耗进度、公共池剩余、本月预计结算金额。

**两条固定提示文案**（加入对话框 + 车内用量页均需展示）：

1. **周刷新提示**："锁定额度按周计算，每周自动刷新，未用完不结转。"——避免用户误以为额度是月度一次性发放的；
2. **消耗顺序提示**："用量优先消耗你的锁定额度，锁定部分用完后才使用公共池；公共池全员共享、先到先得，不保证可用。"——管理用户对公共池的预期。注：限额实现上保底（r）与公共池（C）分别由"保底分支无条件放行"与组级计数器执行（§4.2 v3.2），"先锁定后公共池"在该机制下天然成立（只有越过 r 的用量才占用公共池）。

## 5. 激励相容性分析

| 行为 | 收益 | 代价 | 结论 |
|---|---|---|---|
| 如实申报 | 保底够用；计费≈实际，几乎无退补 | 无 | **严格最优策略** |
| 低报 | 少付押金 | 保底只有 0.8×低报值，超额要去公共池抢；结算按实际用量照付 | 无套利，自我惩罚 |
| 高报 | 保底变大 | **至少按 80% 申报值付费**（地板规则），虚报部分直接变成多付的钱；挤占 105% 上限（声誉成本） | **稳定亏钱，被规则消除** |
| 多拉人 | 席位费 400/N 下降，全员受益 | — | 鼓励拼车 |

公共池先到先得会被重度用户优先吃掉——这是设计意图（鼓励多用），且规模被限制在 16–20%，不影响保底公平性。

### 6.2 限额执行变更（v3.2 重写）

`user_subscriptions` 新增两列（migration 187 / 189），ent schema 同步：

- `weekly_limit_usd` —— 订阅级周限额覆盖（NULL 回退 group 级）；
- `weekly_reserved_usd` —— 拼车保底 r（NULL = 非拼车订阅，行为与现状完全一致）。

限额检查两层一致执行（中间件 `ValidateAndCheckLimits` 与 billing cache `checkSubscriptionEligibility`）：

```
limit = sub.WeeklyLimitUSD ?? group.WeeklyLimitUSD   // 订阅级覆盖优先（个人上限 r+C 防呆）
usage < sub.WeeklyReservedUSD           → 无条件放行（保底，不读计数器）
usage ≥ sub.WeeklyReservedUSD           → 组级计数器 used < C 才放行
```

- 拼车组开车时：group `weekly_limit_usd = 2400`（每订阅语义的安全帽），每个成员订阅写入 `weekly_reserved_usd = 0.8×申报`、`weekly_limit_usd = r + C`，并把全车 `weekly_window_start` 对齐到发车日零点；拼车订阅的周重置吸附回该 7 天网格；
- 组级公共池计数器（`service.CarpoolCommonsCounter`，Redis 实现 `repository/carpool_commons_cache.go`）：key `carpool:commons:{group_id}:{window_start_unix}`，INCRBYFLOAT 原子累加，GET 预检查；计数器由 `BillingCacheService` 持有并注入（`SetCarpoolCommonsCounter`），未注入/读取失败时跳过公共池强制（fail-open，保底不受影响）；
- 公共池容量 C 无需单独存储：发车时全车按同一公式写入 `weekly_limit_usd = r + C`，任意成员订阅可派生 `C = weekly_limit_usd − weekly_reserved_usd`；
- 计费提交时在同一 `UPDATE ... RETURNING` 内算得增量 `max(0,新−r) − max(0,旧−r)`，post-commit best-effort 累加计数器（`finalizePostUsageBilling` → `AddCarpoolCommonsUsage`，失败仅记 ALERT）；legacy 降级计费路径（`usageBillingRepo == nil` 的 `postUsageBilling`）不维护计数器（仅测试/降级场景，见 §7）；
- 非拼车组：订阅级两字段均为 NULL，所有新分支按字段存在性守卫，行为与现状完全一致（有回归测试）；
- `GetUsageProgress`（`subscription_service.go:1141`）同步优先读订阅级限额，成员"我的用量"卡片直接展示保底+机动的消耗进度。

### 6.5 不做的事（明确边界）

- 不接入真实支付，结算单仅供线下转账参考；
- 不做周中释放/额度交易；
- 中途上车 v1 按整周申报、整月预付，月末按实际用量结算（公式天然兼容，无需按天折算）。

## 7. 风险与遗留问题

1. **$2400 与上游真实周限的校准**：USD 等价值需按平台计费倍率和上游 Pro 20x 实际限制实测校准，建议先保守（如按 2200 跑几周）再上调；校准不准会集体触发上游 429。
2. **400/人数 的中途变化**：中途加人摊薄席位费，已付差额在月末结算时统一找齐（记入结算单）。v3.3 落地：`carpool_members.quoted_prepaid_amount_cny`（migration 190）留存**上车当时报给用户的金额**，发车只重写 `prepaid_amount_cny`（按发车人数），结算的席位费退补 = 报价席位费部分 − 席位费/发车人数。此前两者用的是同一列，发车时被覆盖，差额恒为 0——"找齐"是段死代码，而钱是按上车报价实收的。历史行回填为锁定值，退化为原来的恒 0，不会凭空造出退款。
3. **公共池预检查的 TOCTOU 语义**：组级计数器是"读 < C 放行、事后累加"的预检查，并发 in-flight 请求可同时通过，带来有限超卖（量级 ≈ 并发数 × 单请求成本）——与既有 `CheckWeeklyLimit` 同级语义，接受；`Σ用量 ≤ 2400` 的不变式允许按此量级被暂时突破。计数器累加是 post-commit best-effort，极端情况下（提交成功但 Redis 写失败）会少量少计（fail-open 方向，仅影响公共池）。
4. **Redis 故障期间公共池强制降级（fail-open）**：计数器读取失败或未注入时跳过公共池检查——保底硬保证不受影响（不依赖计数器），但公共池可能超用；故障恢复后约束自动恢复。选择 fail-open 而非 fail-closed 的理由：公共池在产品语义上"不保证可用"，而 Redis 在本平台其余计费链路均按缓存/best-effort 对待，不引入新的硬依赖。v3.3 补充：**key 缺失不再等同于 0**——`GetCommonsUsage` 在 miss 时回到订阅表重算 `Σ max(0, weekly_usage_usd − weekly_reserved_usd)` 并回填（取 `max(现值, 重算值)` 合并）。原实现下 Redis 重启/`FLUSH`/`maxmemory` 驱逐会让全车凭空再得一个完整公共池 C；只有"读失败"这条路径仍是 fail-open。未配置 Redis 时启动打 ERROR 日志，不再静默关闭公共池强制。
5. **管理员手工重置周窗口会使该成员偏离共享网格**：`AdminResetQuota` 仍按"当天零点"重置；对拼车订阅执行后，该成员的窗口起点脱离发车网格，其超额消耗计入私有计数器 key（方向为少计/fail-open）。运营上对拼车成员避免手工周重置；如需根治可让管理端重置也走网格吸附。
6. **legacy 降级计费路径不维护计数器**：`postUsageBilling`（`usageBillingRepo == nil` 时的兜底，仅测试/灾难降级出现）直写 DB 不算公共池增量；生产经 wire 注入 `usageBillingRepository`，正常不触发。
7. **`ended` 状态仍无写入路径**：可顺带补"订阅全部到期 → 车置 ended"，非本方案必需。
8. **均价指标的口径沟通**：2400 是周限额（USD），1400 是月总价（CNY），均价是混合口径——前端文案需写清。
9. **地板规则的预期管理**：成员必须在上车前明确知道"未用满也至少按 80% 计费"，否则月末结算必起纠纷。前端加入对话框的实时预览里要显著提示。

## 8. v3.3：代码审查修复清单

四路代码审查（安全 / 后端逻辑 / 限额集成 / 前端）后的修复。按"为什么必须改"排序。

### 8.1 安全与越权

| 问题 | 原状 | 修法 |
| --- | --- | --- |
| 群二维码 IDOR | 任何登录用户可拉任意 ID 的二维码，且 `Cache-Control: public` | 按可见性授权：admin / 车主 / 成员始终可读；招募中的 public 车对登录用户开放；招募中的 invite_only 车必须带 `?token=` 且该邀请指向这辆车；缓存头改 `private`。私密车的群二维码等同入场券，原状等于绕过 List 的可见性控制 |
| 车名未转义进 HTML 邮件 | 三处通知邮件直接 `%s` 拼接车名 | 统一走 `carpoolDisplayName`（`html.EscapeString`）。车名是车主自由输入的，未转义等于让车主以平台名义向 admin 和全体成员投递任意标记 |
| 咨询入口无限流 | 任意登录用户可脚本化向全部 admin 邮箱灌邮件，且同步发送挂在请求上 | 每用户 30 分钟冷却（超频 429）、备注截断 500 字符、改异步派发 |
| 无路由级请求体上限 | 落到全局 256MB，且 base64 解码前要全量拷贝 | 创建 8MB、咨询 64KB |

### 8.2 额度参数自助收口（原"参数校验缺口"，实际严重性更高）

`createCarpoolRequest` 把 `weekly_limit_usd` / `reserve_ratio` / `launch_max_ratio` / 席位费 / 变动池全部开放给任意登录用户，只校验 `weekly_limit_usd ≤ 1e9`。任何人都能建一辆"整车周限额 $10 亿"的车，发车时这些参数原样写进 group 与订阅限额（只有 admin 点启动这一道人工闸）。

- 非 admin 传任何非零额度参数 → 403 `CARPOOL_CUSTOM_PARAMS_FORBIDDEN`（拒绝而非静默忽略，免得调用方以为参数生效了）；
- admin 侧新增校验，其中最关键的是 **`reserveRatio × launchMaxRatio < 1`**：该乘积 ≥ 1 时公共池 `C ≤ 0`，而 `CarpoolSharedPoolCapacityUSD` 在 `C ≤ 0` 时返回 0、调用方据此**跳过整个公共池检查**——组级硬约束会静默失效，比"负公共池"严重得多；
- owner 申报同时受申报下限与 `launch_max × 周限额` 约束（超过整车上限的车永远进不了发车区间，会一直卡在 recruiting）。

### 8.3 申报下限与成员上限

- `CarpoolMinDeclaredWeeklyQuotaUSD = 20`（≈1/6 个 Plus）：没有下限时 $0.01 即可占一个席位并拿到公共池准入；
- `CarpoolMaxMembers = 30`：发车是单事务、逐成员建订阅，成员数直接决定该事务的大小。

两者都是可调常量，属于产品口径，需要时改常量即可。

### 8.4 并发与事务

- **AB-BA 死锁**：`JoinByInvite` 原来先锁 `carpool_invites` 再锁 `carpools`，而 `Cancel` 顺序相反。统一为 **carpools → carpool_invites**（父表在前）：先不加锁解析邀请拿 `carpool_id`，锁住车行后再锁邀请行并在锁下复核有效性（撤销 / 过期 / 用完 / 指向的车是否一致），与原来的 `FOR UPDATE` 解析等价。
- **零申报 owner 白嫖**：`declared = 0` 的车主原来照样在发车时拿到订阅——保底 `r = 0`、无地板、无预付，却有完整的公共池准入，正是地板规则要防的搭便车。发车时跳过并置为 `left`，不进结算、不摊席位费。

### 8.5 撤销 + 重新分配会丢掉保底

撤销订阅是**软删除**，而 `ExistsByUserIDAndGroupID` 看不到软删行 —— 所以管理员"撤销某成员的拼车订阅，再重新分配到同一分组"会走 `createSubscription` 新建一行，而这一行没有 `weekly_limit_usd` / `weekly_reserved_usd`。

后果比"限额丢失"更糟：

- 该成员没有保底（`HasWeeklyReserve()` 为 false），其超额用量**不计入组级公共池计数器** —— 对公共池完全隐形；
- 个人上限回落到分组级的 `group.weekly_limit_usd`，也就是**整车的 2400** —— 一个人可以合法烧穿全车。

修法：`createSubscription` 在写入前从同一 `(user, group)` 最近一条订阅（含已撤销的）继承这两个字段。查不到或查询失败时保持原样、不阻塞分配。查询能力做成可选接口 `subscriptionHistoryLookup` 而非塞进 `UserSubscriptionRepository`——后者被大量测试桩实现，扩接口会造成无谓的改动面。

### 8.6 confirmed 状态的出口

原来车主确认后只能等 admin 启动，通知全靠一封可能丢失的邮件，后台没有任何清单，前端也没有入口（`cancel` 对 confirmed 只开放给 admin，而 UI 根本没渲染按钮）——车会连人带钱无限期挂起。

- `POST /carpools/:id/unconfirm`：车主或 admin 把车退回 recruiting，成员与申报全部保留、重新开放上车，并清空 `launch_notified_at`（下次再进区间可重新通知）；
- `GET /carpools/pending-launch`（admin）：列出全部 confirmed 的车，带等待时长与超过 24 小时承诺的 `overdue` 标记；前端在拼车页顶部渲染为待启动横幅，可直接启动；
- 前端补上 confirmed 车的取消入口（admin）与撤回确认入口（车主/admin）。

### 8.7 结算与前端

- 结算单带上邮箱/用户名（仅 owner/admin 的全量视图）：只有 `#userId` 时车主没法把每一行对应到微信群里的真人收款；
- 加入对话框把"该车当前均价"换成**"你的折算单价"**并实时计算，偏离均价 20% 以上时额外提示。席位费按人头均摊、变动池按申报分摊，申报越小单价越高——拿均价当报价对轻度用户是系统性低估（本文档 §4.6 自己举过"轻度用户实际单价可能是均价两倍"）；
- 申报推荐的异步响应加序号防护：迟到的响应不再回写金额输入框，也不覆盖用户已改过的数字；
- 邀请对话框加序号防护：连点两辆车的"邀请"时，不会出现"显示 B 车、链接是 A 车"的错配；
- 后端错误码全量映射为中文提示（`carpool.errors.*`）：超额度、车满这类是核心拒绝路径，必须告诉用户下一步能做什么，而不是把英文原文抛出来。

### 8.8 结算落库（settled_at 不再是死列）

migration 187 加了 `carpool_members.settled_at`，但**没有任何地方写它**：结算单每次读都按当下数据重算。做预览没问题，做**财务记录**是错的——`actual_usage_usd` 读的是 `user_subscriptions.monthly_usage_usd`，它一直在动，所以车主按 A 收的钱，任何人第二天读到的是 B。

migration 191 补上冻结机制：

| 端点 | 权限 | 作用 |
| --- | --- | --- |
| `POST /carpools/:id/settlement/settle` | 车主 或 admin | 冻结结算单 |
| `POST /carpools/:id/settlement/unsettle` | 仅 admin | 撤销冻结，回到实时预览 |
| `GET /carpools/:id/settlement` | 成员/车主/admin | 已结算返回快照，未结算返回实时预览 |

**为什么车主也能结算**：车主是实际收退款的人，需要能把自己账本上的数字钉死。`settled_by_user_id` 留审计；撤销收敛到 admin，避免车主反复重算。

**冻结哪些字段**：地板用量、实际用量、计费用量、变动池分摊、席位费、合计退补——把渲染整张单子需要的数字全部存下来，因此已结算的单子既不依赖实时用量，也不依赖车辆参数保持不变。`floor_triggered` 由 `实际 ≤ 地板` 推导，不单独存。申报值、邮箱这类展示字段仍取实时值（改了邮箱应该看到新的）。

**幂等**：车行的 `settled_at IS NULL` 是守卫（`UPDATE ... WHERE settled_at IS NULL` 的 affected 行数），两个人同时点"结算"时后到的拿 `CARPOOL_ALREADY_SETTLED`，不会覆盖已冻结的账单。结算写的是**全车**成员，不受调用者可见性裁剪影响——普通成员视图只有自己一行，按它落库会把别人的账丢掉。

**降级**：某一行缺快照（结算后手工插入的异常数据）时该行保留实时值，不伪造历史。

### A1 满车场景（Σ申报 = 2400，均价恒为 ¥70/Plus等价）

|---|---|---|---|---|
| 重度拼车 | 6 人 | $400/周 | 66.7 + 166.7 = **¥233/月** | 3.3 个 Plus |
| 均衡拼车 | 10 人 | $240/周 | 40 + 100 = **¥140/月** | 2 个 Plus |
| 轻度拼车 | 20 人 | $120/周 | 20 + 50 = **¥70/月** | 1 个 Plus |

### A2 混合场景（12 人满车：2 重度 + 6 中度 + 4 轻度）

| 成员 | 申报 | 预付 | 相当于 | 折算单价 |
